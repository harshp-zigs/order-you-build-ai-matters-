# The Order You Build AI In Matters More Than the AI You Build

> Same model. Same budget. Same team. Different order. Opposite result.

One launches a customer-facing assistant in month two, then discovers its product data is scattered across four systems and spends the rest of the year patching answers. ## The Dependency Rule

Every AI capability sits on top of something else. Draw the chain before you commit to the order:

```
 Clear goal ──► Usable data ──► Connected systems ──► Working use case ──► Real adoption ──► Scale
```

Each arrow is a dependency. If you start on the right side while the left side is still weak, you will not skip the earlier steps. You will pay for them later, under deadline pressure and in front of users.

**The rule:** never schedule something before the things it depends on.

## Four Sequences That Quietly Fail

**1. Showcase first.** The most impressive demo gets built first, usually a chatbot or assistant, because it is easy to present. It then has no reliable knowledge underneath it. *Fix:* build the knowledge base or data layer first, and show the assistant second.

**2. Everything at once.** Five projects start in the same quarter, each competing for the same data team and the same executive attention. None gets finished well. *Fix:* choose one first win and let the others wait their turn.

**3. Scale before proof.** A pilot works in one team, so it is rolled out to the whole company before anyone measured why it worked. *Fix:* write down the pilot's result and the conditions behind it, then expand to one more team, then the next.

**4. Governance as an afterthought.** Security review, access rules and monitoring are planned for "after launch." The launch then stalls in review, or ships with gaps that are expensive to close. *Fix:* put the basics in the first phase and deepen them as the program grows.

## The Next-Step Test

Run every item on your roadmap through three questions:

| Question | Why it matters |
| --- | --- |
| **What does it need that does not exist yet?** | Anything missing becomes a prerequisite and moves earlier in the plan. |
| **What does it unlock once it works?** | Items that unlock many others deserve an earlier slot. |
| **How costly is it to undo if we are wrong?** | Cheap-to-undo items go first, because they teach you the most for the least risk. |

Order the list so that cheap, high-unlock items come first and expensive, hard-to-reverse items come last, after the evidence is in.

## Quick Answers

**Is a roadmap just a project plan?**
No. A project plan schedules tasks for one project. A roadmap decides which projects to run, in what order, and why.

**How detailed should it be?**
Detailed for the next phase, rough for the ones after. The later phases should change as you learn.

**When should we bring in outside help?**
When your ideas outnumber your capacity, when earlier pilots stalled, or when teams disagree on priorities. A neutral view of the sequence often settles arguments that data alone cannot.

**What if our roadmap is already underway?**
Run the Next-Step Test on what remains. Moving one item earlier or later is often cheaper than it sounds.
